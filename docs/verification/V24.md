## What the gate runs

1. `gh repo clone GlassOnTin/fieldsmith -- --recurse-submodules` into a fresh temp dir.
   The repo is private, so the gate needs a gh auth with repo scope on the box; a plain
   `git clone` cannot see it. The submodule `fenics-rs` checks out at the pinned rev
   `14b0dc8` and its workspace keeps its own root (`exclude = ["fenics-rs"]` in the
   fieldsmith `Cargo.toml` — before that line, cargo resolved the submodule's
   `authors.workspace = true` inheritance against fieldsmith's root and failed).
2. `cargo build --workspace` in the clone, nothing else present. The caller's
   `CARGO_TARGET_DIR` is unset so the clone builds cold in its own `target/`; `~/.cargo`'s
   registry cache is left as the user's own (a first-ever build also downloads the
   registry — that cost is not in the 104 s).
3. The pinned golden question — the `ladder-ok` case of
   `crates/fieldsmith-verify/tests/fixtures/v22-golden.jsonl` (apiv 2, the reference
   bracket, rungs `[30000, 150000]`) — is built from the **clone's own**
   `examples/bracket.fsm` and driven through the clone's `fieldsmith api` verb with
   `FIELDSMITH_COSTS_STORE=/dev/null`. The answer's canon (the V22 transform: the
   timing leaves dropped, every float quantized to 6 significant digits, keys sorted)
   is byte-compared against the fixture line's own canon text. The engine identity
   travels inside the canon, so a version bump breaks the tie — the named, never
   silent, change; re-bless through `v22_api` with `FIELDSMITH_BLESS=1` in a recorded
   commit.
4. The canon comparator is python in the gate script, and it is validated inside every
   run, not trusted: the gate first canon-compares **the tree's own** verb run against
   the same fixture line and requires the byte-tie before the clone's answer is
   compared. Two implementations of the V22 transform (the Rust one that blessed the
   fixture, this Python one) cannot drift without the gate failing loudly.
5. `data/costs/costs.csv` is byte-compared clone vs tree: the cost store's seed rows
   travel with the clone, which the costs-rows-via-PR story depends on.

The gate's first run failed on a harness bug in this script's comparator (a trailing
newline carried by `readline()`; not a contract failure) and was fixed in the commit
that introduces it. Both runs measured the same walls for the contract legs.

## Credentials scan before the first push

Patterns run against the tree before the first `push`: PEM `BEGIN PRIVATE KEY` blocks,
`ghp_`/`gho_`/`github_pat_` tokens, `AKIA` access keys, `sk-` API keys, and tracked files
with secret/token/key in the name. Findings, whatever they were: **no credentials in the
tree.** The one name hit, `crates/fieldsmith-worker/src/token.rs`, is the enrolment
token's FORMAT module — source code that handles credentials, holds none (the token is
printed once by the operator and stored 0600 by the worker). Docs carry prose mentions
of `/tmp` tooling paths (build/extract workspaces); they name no secrets and were left.

## Not verified here

- One host, one run position: the 104 s is this workstation (x86_64) with a warm
  `~/.cargo` registry cache. A cold registry adds download time — not measured.
- Non-x86_64 clone hosts are not covered by this gate; the ARM datapoint (M18/V25)
  carries the aarch64 build separately.
- Raw-envelope float bit-identity across machines stays out of scope (V22's named
  gap): the canon quantizes to 6 significant digits, and that is what the tie proves.
- The submodule workflow (`git submodule update` after a pin bump) is part of the
  normal build route but is exercised by this gate only in the fresh-clone direction.
